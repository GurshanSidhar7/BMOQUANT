01 / READ THE FILESee the code ↗

Start with one row per stock, per date.

The input is a CSV: a plain-text spreadsheet. Each row tells us what happened to a stock’s price and trading volume on a particular date.

An example of what arrivesActual rows from the synthetic file
Example raw price records
Ticker Trade date Close price Shares traded

What do these words mean?

Ticker identifies the stock. Close is its price at the end of the day. Volume is the number of shares traded. The full file also includes the opening, highest, and lowest prices.

Why keep the original row?

If a record fails a check, we need to point back to the file and row it came from. The project keeps that information alongside the data.

After this step: we know what arrived and where every record came from.

02 / MAKE IT CONSISTENTSee the code ↗

Give every field one clear meaning.

Files can use different names and formats. A short configuration tells the project which column means “stock,” which means “date,” and how to read each value.

FROM THE FILEIN THE DATASET
ticker: " syn0001 "→ symbol: "SYN0001"
trade_date: "2025-01-02"→ A proper date
close: "101.50"→ A decimal number: 101.50
volume: "250000"→ A whole number: 250000

Illustrative values. The same rules are applied to every row in the file.

A value such as not-a-date cannot become a real date. It is marked as a parsing error so it can be reviewed in the next step.

After this step: the columns have consistent names and types. Formatting mistakes are visible.

03 / CHECK THE RECORDSSee the code ↗

Separate broken records from unusual ones.

A negative price is invalid. A big price jump could be real. Those need different treatment.

ERROR → SET ASIDE

Something is unusable or ambiguous.

A missing stock name, a broken date, a nonpositive price, negative volume, inconsistent high/low prices, or a repeated stock/date/source.

The record is saved separately with its reason. This is called quarantine. Both copies of a duplicate are set aside.

WARNING → KEEP & FLAG

Something deserves a closer look.

A very large return, a sudden volume change, several unchanged prices, or a gap between expected weekdays.

The record stays in the dataset. A warning says “review this”; it does not prove the value is wrong.

What if the file should be rejected entirely?

The configuration can stop the run when a chosen category fails, instead of continuing with valid rows. A required missing value stops a run by default; this demonstration explicitly allows quarantine. A rejected run leaves the previous saved dataset active.

After this step: the retained records can be used, and the rejected records remain available for review.

04 / ADD USEFUL MEASURESSee the code ↗

Turn prices into simple research inputs.

The project sorts the retained rows by stock, source, and date. It then calculates the same measures for each stock using only its current and earlier observations.

1 / PRICE RETURN

How much did the price change?

If yesterday’s close was 100 and today’s close is 102, the price rose by 2%.

return = today’s close ÷ previous close − 1

“Previous” means the previous retained observation. A missing date means the return spans that gap.

2 / RECENT VOLATILITY

How uneven have price moves been?

Look at the last 20 log returns and measure how much they vary. A higher value means larger recent swings. This describes what happened; it does not predict the next move.

Needs 21 prices to produce 20 returns. Until then, the value is blank.

3 / AVERAGE VOLUME

How much has the stock traded?

Average the number of shares traded over the last 20 observations. This provides a simple picture of recent trading activity.

A volume measure alone does not establish that a trade can be executed easily.

Show the precise calculation choices

Volatility is the sample standard deviation of 20 trailing log returns, multiplied by √252 to express it on an annualized scale. A log return is ln(current close) − ln(previous close). The library also exposes 30-return volatility and approximate dollar volume (close × volume).

Groups stay separate by stock and data source. Missing observations are never filled in. Analytics are calculated before a researcher selects dates, so the first displayed date can use earlier history. If a derived calculation exceeds the supported numeric range, the run stops for input review instead of repeatedly removing rows.

After this step: the dataset contains prices plus a few consistently calculated measures.

05 / SAVE & USE ITSee the code ↗

Give the next analysis a dependable starting point.

Save the cleaned data as Parquet: a compact file format that remembers dates and number types. Save the quarantined records and a report alongside it.

DATA

prices.parquet

The retained records and calculated measures, ready for analysis.

REVIEW

quarantine.parquet

The records set aside, their original values, and the reasons.

REPORT

report.json

Row counts, warning counts, input fingerprints, and run settings.

How does someone use it?

A Python script or DuckDB query can select a stock and a date range from the saved file. DuckDB is a local tool for asking spreadsheet-like questions using SQL.

What happens on the next run?

The project saves a new complete version, then marks it as current. A rerun replaces the active dataset instead of appending duplicate rows. A failed run keeps the previous version available.

WHAT THIS PROJECT DEMONSTRATES

A useful tool with a modest scope.

Repeatable cleaning and basic descriptive analytics for local research. The walkthrough uses 10 generated stocks to make checks repeatable. The workspace also includes frozen 2025 NVIDIA, SanDisk, and EIA WTI spot-price histories.

What it handles

CSV files, explicit data checks, a small set of calculations, saved versions, and local Python/SQL access.

Where it stops

Live feeds, split/dividend adjustments, trading, forecasts, and shared production operations are outside this project. Weekday checks approximate a calendar and can flag holidays.

Supporting evidence, tests, and measured performance

Python verification is available in the repository.

Tests compare returns and volatility with independent numerical references, check source boundaries and earlier history, and verify that publication failures preserve saved data.

The separate benchmark exercise compares matched workloads at 100k and 1M synthetic rows. Its machine-specific results are supporting evidence; the value of this utility is consistent preparation of research data.
