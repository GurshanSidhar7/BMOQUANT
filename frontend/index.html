WHY THIS MATTERS

Real files arrive with different headers, malformed dates, repeated observations, and missing values. A correct analysis starts with a consistent interpretation of those files.

Files are discovered in a deterministic order. Each row retains its original file and record number, so an error can be traced back to the input.

A SAFE REPEAT

Identical input creates a new audited snapshot, not an append. The active logical dataset has the same records. Readers resolve one version and finish against it.

A DELIBERATE BOUNDARY

Single writer, local filesystem. Old snapshots are retained. Atomic visibility is not a distributed transaction or a power-loss durability guarantee.

Where does lazy processing become eager?

CSV scanning, normalization, and casts form a lazy query. The pipeline materializes the normalized dataset before global duplicate detection, record-level quarantine, sorted analytics, and reporting. That boundary favors a simple, auditable MVP over an out-of-core claim.

What prevents look-ahead bias in the calculations?

Each lag and rolling window stays within a symbol/source group and uses only current and prior retained observations. Tests confirm appending future rows does not change history. Closing prices become available after the close; downstream strategies must still model later execution and point-in-time availability.

Why Polars and DuckDB together?

Polars owns normalization, validation, and canonical financial analytics. DuckDB provides embedded SQL over the resulting Parquet snapshot. Their capabilities overlap; every pipeline stage does not need to pass through both engines.

What does reproducibility mean here?

The same seed, input contents, configuration, and locked software versions reproduce the logical records and financial values. Input SHA-256 fingerprints and recorded settings establish a trail. Run IDs and timestamps intentionally differ.
